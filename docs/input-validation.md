# External input validation

The operation matrix is [input-validation.json](input-validation.json): 467 HTTP registrations
(including app/public shared routes and admin routes), 104 MCP tools, and four client Socket.IO
operations. Each HTTP row declares path, query, body, headers and cookies; signature webhooks also
declare raw bytes. The keys identify the source module, method and route. Repeated registrations
in one module have an occurrence suffix because app/public implementations can differ.

`validated` means the row names a runtime validator or parsing boundary. `reviewed` is an explicit
exception, including unused input, authenticated protocol values, or permissive import formats.
Neither registration coverage nor the presence of a schema proves that every domain rule is
correct. Membership, ownership, subscription status, card activity state, quotas and permission
checks remain separate from shape validation. Existing authentication hooks and handler ordering
are retained; malformed authenticated UUID inputs fail before database access with the existing
translated `400 VALIDATION` envelope. Signed media and invitation lookups retain concealed 404s.

New board query contracts accept literal `true`/`false` strings (transfer targets also retain `0`/`1`), and decimal-digit integer strings only. Missing fields keep their prior defaults; empty strings, arrays and malformed values are rejected. Completed ranges accept both dates and ISO instants. Existing shared query DTO coercion policies remain visible in their schemas; this change does not silently redefine every historical query contract.

## Enforcement and maintenance

`pnpm lint:input-validation` (also part of `pnpm lint`) discovers supported registrations using the
TypeScript AST, including inline/named handlers, local helpers passed the request, `app.route`,
MCP tools and Socket.IO events. Unknown dynamic registration forms on the known Fastify receivers,
imported unresolved handlers and dynamic tool/event names fail rather than silently disappear.
The scanner tracks request parameter aliases and direct multipart reads. Imported request helpers
and raw Node transport behavior are declared in the matrix and this table.

A new operation requires all applicable declarations. A changed handler (including expanded local
request helpers) invalidates its SHA-256 review fingerprint. Declared direct validator text must
still exist, referenced files/symbols must exist, and shared DTO/helper evidence files have review
fingerprints. This is a review gate, not data-flow analysis or proof that arbitrary future routing
styles are discoverable. Adding a new server/transport pattern requires extending the scanner.

Run `node scripts/check-input-validation.mjs --inventory` to inspect the discovered operations,
inputs, helper forwarding and validator expressions. After reviewing a change, update the affected
matrix declarations and fingerprints; do not mechanically refresh fingerprints to make lint pass.
Hashes use the handler text shown by that command and file bytes for `evidenceFiles`. Reuse a
matching declaration profile only when its validator or exception actually applies to that input.

The E2E validation spec exercises malformed workspace IDs, rejected JSON writes, cursor compatibility,
exact/submillisecond ties, malformed Socket.IO payloads, missing acknowledgements, and the absence
of rejected-write realtime effects with a valid public-write control. The direct-input tests also cover impossible dates, malformed/nonfinite numbers, decoded archive fields, Unicode storage constraints, replay nesting, embedded identifiers and sender-header/protocol injection. Separate outbound and content-sanitization specs cover rejected push registration/rotation and stored-content rendering at desktop/phone widths. The import regression spec rejects invalid archive scalars both during analysis and when committing older stored plans, then round-trips valid zones, option positions and reactions. Media/export E2E also rejects private attachment copies while restoring an accessible expired attachment. Deterministic transport tests exercise DNS pinning, response streaming limits and unsolicited MCP callback upgrades that ordinary E2E cannot force reliably. Existing MCP checklist and
media/export E2E scenarios cover strict tool arguments, aliases, uploads and concealed signed-media
access. Integration tests retain deterministic push retry/lease and auth rotation signals. Hosted billing route tests reject seat-count overflow before provider calls; the normal self-hosted E2E stack deliberately rejects billing before parsing its payload.
